# Coldsea 的“2954～2956未知语句”：文件审计与安全处理

## 观察到的事实

用户附件 `Forbidden_coldsea3.spc`：36490字节、1479物理行，SHA-256：
`09b9dc3a3c0d2d6356d7ffa8a76d46349c0ac12f00079bdb23c3bfe500f0ff01`

| 类型 | 条数 |
|---|---:|
| chart | 1 |
| tap | 633 |
| hold | 180 |
| flick | 250 |
| skyarea | 412 |
| bpm | 3 |

1475条音符记录不是最终combo物量。源文件末尾实际是：

```text
1477: bpm(137931,174.0,99.0)
1478: bpm(140000,174.0,4.0)
1479: bpm(140690,174.0,4.0)
```

三条BPM仍为174，第三字段是每小节拍数。137931开始临时设为99拍一小节，140000恢复4；140690再次重置本段小节起点。它们不是99轨宽/滚速/新note类型。按本编辑器的规则，每个bpm自身都画小节线，上一段停止于下一段开始；99拍的完整下一小节在后面，但在此之前已被140000的新段截断。

原Rust editor `src/chart/codec/methods_parse.rs` 中 `parse_bpm` 接受正beats，包括99。我们的明文SpcDocument同样识别。
源：[固定版本parse_bpm](https://github.com/yuhao7370/In_Falsus_Editor/blob/d61cd73395ebe6959358f2f5669ba9cf259eadeb/src/chart/codec/methods_parse.rs#L193-L218)。

## 为什么界面变成2954～2956？这是推断，不是已读取的本地工作文件

ICP JSON转换器的头部有3行，每条成功note输出source注释+语句2行：`3+1475*2=2953`。接着输出3条事件，位置恰为2954、2955、2956。

这与用户报告高度吻合：来源可能是已有JSON中未解明事件，被包装成`icp_event(time,type,base64)`保留。我们没有拿到这首Coldsea的JSON或用户本地 `.ifstudio/Charts` 文件，**不声称看到了那三条真实包装，也不硬编码一个未知type或载荷偏移**。

## v0.9做了什么

1. 保留所有opaque原记录；“高级未识别内容”中显示time、type和可安全读取的JSON字段名。
2. JSON明确给出正数`bpm`与`beats_per_bar`时可转成合法bpm；只有无名二进制payload时继续保留，不能凭type编号猜。
3. 增加“从配对明文补入 BPM/拍号”。用户明确选文件，先核对相同头部及所有已知音符的时间、几何、group、方向、缓动，再把缺少的bpm逐行原样加入RAM。
4. 已有同时间不同BPM/拍数冲突、音符已修改不匹配、未解明note等情况整次拒绝；不覆盖现有编辑，不删除未知事件，不把文件名一致当匹配。
5. 成功补入一次Undo可全部撤销，Ctrl+S之前不写文件；重复导入不重复加bpm。

也可以直接加载这份明文查看；此路径会离开当前歌曲工程，按现有Save/Discard确认流程处理。Fixtures中含附件原字节副本作本地回归。

若仍有未知提示，请保留未知原文及关联JSON并用于后续解码：提示存在不意味着已有BPM没生效，也不是删掉未知行的理由。
